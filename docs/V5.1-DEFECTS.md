# Defects in HOMER v5.1

This file lists 63 defects in HOMER v5.1 as released (`homer.v5.1.zip`, sha256 `abaa6a1e9a8df902a423fb403dd2d7a85a3cf7706ab4ae099e4a4cfb0e621b12`), found while homer2-ao's output was compared with v5.1's, file for file, and while the test suite in `tests/` was written. File and line numbers are those of v5.1. The test suite does not assert any of these behaviours, so fixing one will not break it.

The homer2-ao column names commits by their subject: the find commit (`homer2 find: indexed motif scan, ordered output, FASTA read in memory`), the known commit (`homer2 known: index ZOOPS counts, ...`), the norm commit (`homer2 norm: ...`), the denovo commit (`homer2 denovo: faster oligo table, ...`), the `-Tcpus` commit, the background-selection commit (`homerTools: bgbins, randbg and filterids ...`) and the compareMotifs.pl commit. `git log v5.1..` lists them.

Each entry gives what happens, a reproduction where one was recorded, where in the source the cause lies, how it was verified on v5.1, and what homer2-ao does. The homer2-ao column uses five values:

- **fixed**: homer2-ao no longer has the defect, and otherwise gives v5.1's output.
- **behaves differently**: homer2-ao changes the behaviour, but not simply by removing the defect; the entry says how.
- **unchanged on purpose**: homer2-ao keeps v5.1's behaviour so that its output stays identical. The commits that change this code state that its output is as in v5.1, and none lists a change for this case. Unless the entry says otherwise, the case itself was not run on homer2-ao.
- **unchanged (code untouched)**: no commit changes the file or function involved, so homer2-ao has the defect as v5.1 does.
- **not checked**: neither the commit messages nor a run of homer2-ao settle it.

Counts: 5 fixed, 4 behaves differently, 11 unchanged on purpose, 30 unchanged (code untouched), 13 not checked.

Where a defect was found while the test suite was written, or by reading the source, and was not reproduced on its own on v5.1, its **Verified** line says so. Reproductions marked *setup* run in a directory prepared by the setup block below; the others name their inputs, most of them the synthetic files in `tests/data/`.

## homer2: input, scanning and output (find, known, mask, norm)

### 1. `homer2 find -mscore` prints an unset position and strand for a sequence with no scorable window

For a sequence in which no window can be scored (all N, or shorter than the motif), `-mscore` prints the best score -10000000000.000000 with a position and strand that were never set for that sequence. They repeat the values of the sequence scanned before it, or, when it is scanned first, show whatever the buffer held (1515870810 with `MALLOC_PERTURB_=165`). The usage describes `-mscore` as the best motif score per sequence, and such a sequence has no best site.

- **Source:** `cpp/Motif2.cpp:3394-3399` and `3453-3458` set the site only when a window beats -1e10; `3921-3922` allocate the position and strand arrays without initializing them; `3951` prints element 0.
- **Verified:** Reproduced on a v5.1 build (`configureHomer.pl -make`, g++ 13.3.0, Ubuntu 24.04) with the reproduction below, 2026-10-28. It was first found when the find commit's code was compared with v5.1, whose 191 reference outputs held 34.7 million such lines.
- **homer2-ao:** Unchanged on purpose. The find commit rewrites `SequenceArray::motifScan` and keeps this behaviour. The unset values it prints can differ from v5.1's, which is why the comparison of the find commit's code with v5.1 masked these two fields.
- **Reproduction** (*setup*):

  <details><summary>Reproduction</summary>

  ```bash
  python3 - <<'EOF'
  import random
  random.seed(2)
  a, b = (''.join(random.choice('ACGT') for _ in range(200)) for _ in range(2))
  open('allN_middle.fa', 'w').write('>seq1\n%s\n>allN\n%s\n>seq3\n%s\n' % (a, 'N' * 200, b))
  ```

### 2. A tab in a FASTA name is read as the start of the sequence, and about 1,000 tabs corrupt the heap

`parseFasta2SeqAndGroupFiles` copies the FASTA name, tabs included, into tab-separated temporary files, so the text after the first tab is read as the sequence: a site there is reported and the real sequence is dropped. Each tab also adds a column to a fixed array of 1,000 pointers filled without a bound. In the reproduction, 999 tabs make glibc abort (`malloc(): corrupted top size`, exit 134) and 997 run normally; the earlier homer2 report saw a heap overflow under AddressSanitizer from 998 tabs and a segfault at 1,100.

- **Source:** The name is written unescaped at `cpp/Motif2.cpp:3629-3630` and `3649-3650` and split on tabs again at `3692` and `3722`; `splitMotif2` (`534-549`) has no bound; seven functions pass it a `new char*[1000]` (`728`, `1854`, `2949`, `3673`, `5528`, `5696`, `6054`).
- **Verified:** Reproduced on a v5.1 build (`configureHomer.pl -make`, g++ 13.3.0, Ubuntu 24.04) with the reproduction below, 2026-10-28.
- **homer2-ao:** Unchanged on purpose. `known`, `find`, `mask` and `norm` now read FASTA in memory, but input with a tab or CR in a kept byte takes a serial reader that parses the lines the v5.1 round trip would have written (find commit), and the find commit's code reproduced this defect as v5.1 has it. `denovo -i` still uses the v5.1 reader, which no commit changes.
- **Reproduction** (*setup*):

  <details><summary>Reproduction</summary>

  ```bash
  python3 - <<'EOF'
  import random
  random.seed(4)
  s = ''.join(random.choice('ACGT') for _ in range(200))
  open('plain.fa', 'w').write('>seq1\n%s\n' % s)
  open('tab_name.fa', 'w').write('>seq1\tGGTGACTCAGG\tnote\n%s\n' % s)
  for n in (997, 999):
  	open('tabs%d.fa' % n, 'w').write('>seq1' + '\tx' * n + '\n' + s + '\n')
  EOF
  for f in plain.fa tab_name.fa; do echo "$f: $(homer2 find -i $f -m ap1.motif 2>/dev/null | wc -l) site(s)"; done
  homer2 find -i tab_name.fa -m ap1.motif 2>/dev/null
  for n in 997 999; do
  	homer2 find -i tabs$n.fa -m ap1.motif > /dev/null 2> err.txt
  	echo "$n tabs: exit $? $(grep -o 'malloc(): .*' err.txt)"
  done
  ```

  Expected: the same result for `plain.fa` and `tab_name.fa` (no site), and no crash.

  Actual:

  ```text
  plain.fa: 0 site(s)
  tab_name.fa: 1 site(s)
  seq1	-3	TGACTCA	AP-1	+	8.566428
  997 tabs: exit 0
  999 tabs: exit 134 malloc(): corrupted top size
  ```

  </details>

### 3. A FASTA record of 1,000,000 bases or more overflows a fixed buffer

`homer2 find -i` aborts on a FASTA record of 1,000,000 bases (`*** buffer overflow detected ***`, exit 134, with glibc's `_FORTIFY_SOURCE`, which Ubuntu's g++ enables; without it the overflow is silent heap corruption) and reads a record of 999,999 bases normally. The same 1,000,000 bases given as a sequence file with `-s` work.

- **Source:** `SequenceArray::parseFasta2SeqAndGroupFiles` collects each record in `new char[1000000]` (`cpp/Motif2.cpp:3588`) with `strcat` (`3645`); it reads `-i`/`-b` FASTA for `denovo` (`703`) and for `known`, `find`, `mask` and `norm` (`4482`).
- **Verified:** Reproduced on a v5.1 build (`configureHomer.pl -make`, g++ 13.3.0, Ubuntu 24.04) with the reproduction below, 2026-10-28. Comparing the find commit's code with v5.1 also met it on a 4.6 Mb single-line chromosome.
- **homer2-ao:** Behaves differently. Fixed for `known`, `find`, `mask` and `norm`, which read such records in full (find commit); their output matched v5.1's reading the same sequence through `-s`. `homer2 denovo -i` still goes through `parseFasta2SeqAndGroupFiles` and still has the defect.
- **Reproduction** (*setup*):

  <details><summary>Reproduction</summary>

  ```bash
  python3 - <<'EOF'
  import random
  random.seed(3)
  s = ''.join(random.choice('ACGT') for _ in range(1000000))
  for n in (999999, 1000000):
  	with open('rec%d.fa' % n, 'w') as out:
  		out.write('>chrTest\n')
  		for i in range(0, n, 60):
  			out.write(s[i:min(i + 60, n)] + '\n')
  open('rec1000000.seq', 'w').write('chrTest\t' + s + '\n')
  EOF
  for f in rec999999.fa rec1000000.fa; do
  	homer2 find -i $f -m ap1.motif > out.txt 2> err.txt
  	echo "-i $f: exit $?, $(wc -l < out.txt) sites $(grep -o '\*\*\* buffer overflow detected \*\*\*' err.txt)"
  done
  homer2 find -s rec1000000.seq -m ap1.motif > out.txt 2> /dev/null
  echo "-s rec1000000.seq: exit $?, $(wc -l < out.txt) sites"
  ```

  Expected: 126 sites from `rec1000000.fa`, as from the same bases through `-s`.

  Actual:

  ```text
  -i rec999999.fa: exit 0, 126 sites
  -i rec1000000.fa: exit 134, 0 sites *** buffer overflow detected ***
  -s rec1000000.seq: exit 0, 126 sites
  ```

  </details>

### 4. A motif file without HOMER's header line is read without a row bound

`Motif::readMotifFile` skips a missing tab-separated header line but keeps appending matrix rows with no bound at `MAXIMUM_MOTIF_LENGTH` (10,000). Up to 10,000 rows give "0 motifs loaded"; more write past the matrix and segfault. MEME, HOCOMOCO PWM/PCM, TRANSFAC and FIMO TSV files with more than 10,000 rows of four or more tab-separated fields crash this way.

- **Source:** The write past the matrix is at `cpp/Motif2.cpp:2997`.
- **Verified:** Reproduced on a v5.1 build when the find commit's code was compared with v5.1, where ten non-HOMER motif files crashed both builds.
- **homer2-ao:** Unchanged on purpose. The find commit rewrites `Motif::readMotifFile` (the file read once, plain decimals parsed with `strtod`); that code was found to reproduce this defect. No later commit changes the function.
- **Reproduction:** No standalone reproduction recorded here. A seeded reproduction was made on a v5.1 build, but it is not part of this repository.

### 5. A missing or empty `-i`/`-b` FASTA file ends the run with exit status 0 and leaves temporary files

homer2 creates `0<n>.seq` and `0<n>.group` in the working directory before it opens the FASTA files. When one is missing, `known` and `denovo` print `Could not open FASTA file ... !!!` and exit 0, leaving both files; with empty targets, `denovo` prints `!!! Something is wrong - either no target sequences or no background sequences!!!` and exits 0, again leaving both. More generally, homer2 calls `exit(0)` after its own error messages (40 calls), so a failed run cannot be told from its exit status, and temporary files stay in the working directory after a crash.

- **Source:** `DeNovoMotifs::parseFasta` and `KnownMotifs::parseFasta` name the files from the clock (`cpp/Motif2.cpp:681-703`, `4459-4482`); `parseFasta2SeqAndGroupFiles` creates both (`3573-3582`) before it opens either FASTA file and calls `exit(0)` when one cannot be opened (`3599-3609`); empty targets reach `exit(0)` at `900`, before the cleanup at `288-294`.
- **Verified:** Reproduced on a v5.1 build (`configureHomer.pl -make`, g++ 13.3.0, Ubuntu 24.04) with the reproduction below, 2026-10-28. The count of 40 `exit(0)` calls and the files left after a crash come from an earlier comparison with v5.1 and were not re-run.
- **homer2-ao:** Behaves differently. `known`, `find`, `mask` and `norm` read `-i`/`-b` FASTA in memory and no longer create or leave the `.seq` and `.group` files (find commit); whether they still exit 0 here is not checked. `denovo` with a missing file is unchanged (`parseFasta2SeqAndGroupFiles` is untouched). `denovo` with empty targets is not checked: `DeNovoMotifs::readSequence2Tree`, which holds that `exit(0)`, is rewritten by the denovo commit.
- **Reproduction** (*setup*):

  <details><summary>Reproduction</summary>

  Actual:

  ```text
  denovo -i empty.fa: exit 0; !!! Something is wrong - either no target sequences or no background sequences!!!; left behind: 0<n>.group 0<n>.seq
  ```

### 6. `homer2 find` and `find -mscore` write lines in thread-finish order at `-p` above 1

At `-p` above 1 the order of output lines depends on which thread finishes first, so the same command gives different files from run to run and a different order from `-p 1`.

- **Verified:** Seen on a v5.1 build: v5.1 at `-p 4` differed from v5.1 at `-p 1` in `find`, `-mscore` and `mask` when the find commit's code was compared with v5.1.
- **homer2-ao:** Fixed. `find`, `find -mscore` and `mask` give at any `-p` the output v5.1 gives at `-p 1` (find commit).
- **Reproduction:** No standalone reproduction recorded.

### 7. `homer2 mask` masks one sequence from several threads at once at `-p` above 1

At `-p` above 1, threads take motifs, so several threads mask the same sequence at once and the result varies from run to run.

- **Source:** `Sequence::motifScan`, `cpp/Motif2.cpp:3374` and `3410`.
- **Verified:** ThreadSanitizer on a v5.1 build.
- **homer2-ao:** Fixed. `mask` gives each thread a run of sequences and masks each with every motif in file order, as at `-p 1` (find commit). ThreadSanitizer reported no race in `find`, `-mscore` and `mask` at `-p` 4, 8 and 16 on a build with the find commit, and the same check reported this race in v5.1.
- **Reproduction:** No standalone reproduction recorded.

## homer2 known

### 63. On ARM Linux, `homerTools barcodes -qual` keeps low-quality reads and `findMotifs.pl -homer1` finds no motifs

HOMER's C++ assumes `char` is signed, as it is on x86-64 and on macOS. On ARM Linux `char` is unsigned. `homerTools barcodes` keeps each read's lowest quality in a `char` and compares it with the `int` threshold of `-qual`, so a quality below the FASTQ's quality base character wraps to a large value and the read is kept. With `-homer1`, `findMotifs.pl` runs the original `homer` program, which on ARM Linux leaves no `homerMotifs.motifs8`; its cause in that program was not traced.

- **Source:** `cpp/homerTools.cpp:1098` (`char minQualityScore`), compared at `1116` and `1148`.
- **Verified:** HOMER v5.1 built in place on GitHub's `ubuntu-24.04-arm` runner (g++ 13.3.0) failed `test_barcodes_quality[options3-kept3]` and `test_homer1_uses_the_original_homer`; both pass for v5.1 on x86-64.
- **homer2-ao:** Fixed in the pip and uv builds, which compile with `-fsigned-char` on Linux other than x86-64; both tests pass there. A build with `configureHomer.pl -make` on ARM Linux keeps the defect.
- **Reproduction:** `python -m pytest tests -k "barcodes_quality or homer1_uses"` against a v5.1 build on ARM Linux.
